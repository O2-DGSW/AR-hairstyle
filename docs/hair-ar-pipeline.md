## 0. 먼저 — 이 코드는 무엇을 기반으로 하는가

**HairFastGAN Colab 노트북 기반이 아니다. 현재 파이프라인에 GAN은 들어있지 않다.**

기존 탐색(노션 문서)과 이 프로토타입의 관계:

| | 기존 탐색 (Colab/맥북) | 현재 코드 (heddy-v2) |
|---|---|---|
| 접근 | StyleGAN 잠재공간에서 헤어 이식 | 세그멘테이션 + 고전 워핑 |
| 세그멘테이션 | MediaPipe selfie multiclass (6클래스) | SegFormer face-parsing (19클래스) |
| 실행 | Colab T4, 장당 수 초 | 로컬 4070 SUPER, 프레임당 ~16ms |
| 기존 머리 제거 | LaMa / TELEA 인페인팅 (실패) | 시간축 배경 플레이트 (동작함) |
| 실시간 | 불가 | 30fps |

GAN이 빠진 이유는 설계 판단 반, 환경 제약 반이다:

- **설계**: GAN은 장당 수 초가 걸려 프레임당 실행이 원천적으로 불가능하다.
  실현 가능한 자리는 ① 오프라인 에셋 생성 ② 정지 프레임 고화질 캡처 두 곳뿐이다.
- **환경**: 이 PC에 MSVC / Visual Studio / CUDA toolkit이 없다. HairFastGAN은
  StyleGAN2의 커스텀 CUDA 연산(`upfirdn2d`, `bias_act`)을 컴파일해야 하므로
  현재 상태로는 실행 불가. (맥북에서 Colab을 쓴 것과 같은 이유)

→ GAN 통합은 **미착수**. 붙일 자리는 §7에 정리.

## 1. 전체 구조

두 개의 독립 경로가 있고, 트레이드오프가 정반대다.

```
[경로 A] 서버 합성  —  http://<서버>:8080/
  브라우저 웹캠 ──WebRTC(업로드)──> Python 서버 ──GPU 처리──> 합성 완료 프레임
                                                              │
       브라우저 <──────────WebRTC(다운로드)─────────────────────┘
  · 클라이언트는 영상 하나만 재생 → 오버레이 어긋남이 구조적으로 불가능
  · 대신 왕복(인코딩+네트워크+디코딩)만큼 절대 지연이 큼

[경로 B] 로컬 워핑  —  http://<서버>:8080/warp.html
  브라우저 웹캠 → MediaPipe(WebGL GPU) → 캔버스 합성    (서버 왕복 없음)
  · 지연 최소. 서버는 정적 파일만 서빙
  · GPU 무거운 처리(세그멘테이션/GAN)는 못 씀
```

경로 B는 "실시간 추적 레이어는 온디바이스가 맞다"는 가설의 대조군이다.
최종 모바일 앱에서는 이 구조(온디바이스 추적 + 서버는 온디맨드)가 유력하다.

## 2. 모델

### 2.1 얼굴 파싱 — `jonathandinu/face-parsing`

SegFormer를 CelebAMask-HQ로 파인튜닝한 모델. **19클래스**:

```
0 background   1 skin      2 nose      3 eye_g(안경)  4 l_eye
5 r_eye        6 l_brow    7 r_brow    8 l_ear        9 r_ear
10 mouth      11 u_lip    12 l_lip    13 hair        14 hat
15 ear_r      16 neck_l   17 neck     18 cloth
```

**MediaPipe selfie segmenter에서 갈아탄 이유:**

1. **GPU** — MediaPipe Python은 윈도우에서 CPU 전용이다. 실측 98ms/프레임으로
   코어 하나가 포화 상태였고, 그 위에 아무것도 더 쌓을 수 없었다.
2. **클래스 수** — 6개(배경/머리/몸피부/얼굴피부/옷/기타) → 19개. 눈·코·눈썹이
   따로 나오므로 **별도 랜드마크 모델 없이 앵커를 뽑을 수 있다**(§4.6).
3. **계보** — HairFastGAN 계열이 내부적으로 쓰는 face parsing과 같은 계열이라,
   나중에 GAN을 붙일 때 마스크 규격이 그대로 맞는다.
4. **파인튜닝 1순위** — 노션 문서의 파인튜닝 우선순위 1번이 정확히 이 네트워크다.

### 2.2 얼굴 포즈 — MediaPipe Face Landmarker (`face_landmarker.task`)

3D 포즈와 거리 측정 전용. 정규 3D 얼굴 모델로 PnP를 풀어 4x4 변환행렬을 준다.
CPU에서 1.6ms(p95 2.4ms). 매 프레임 돌리지 않는다(§4.7).

## 3. 프레임 파이프라인

경로 A(서버 합성) 기준. 괄호 안은 실측 비용.

```
1. WebRTC 수신                        aiortc → VideoFrame → BGR ndarray
2. 전처리 (0.7ms)                     GPU 업로드 → 512x512 리사이즈 → 정규화
3. 추론 (12~13ms)                     SegFormer, CUDA 그래프 재생 → 로짓 (1,19,128,128)
4. 마스크 (~0.1ms)                    로짓 bilinear 확대 → argmax → 클래스맵 (480,640)
                                      머리 소프트 알파 = sigmoid((머리로짓 − 나머지최대) × K)
5. 플레이트 갱신                       알파<0.2 인 픽셀만 "머리 아님"으로 누적
6. 기존 머리 제거                      플레이트에 데이터 있는 곳만 소프트 알파로 블렌딩
7. 앵커                               눈 무게중심(매 프레임) + 거리 보정 배율(4프레임마다)
8. 헤어 워핑 (~2ms)                    닮음변환 → grid_sample → 알파 합성  ※ 전부 GPU
9. GPU→CPU 전송 1회                    여기서 처음이자 마지막으로 내려온다
10. WebRTC 송출                        VideoFrame, 원본 pts/time_base 유지
```

**설계 원칙: CPU로 내려오는 지점을 딱 한 번으로 유지한다.**
한때 헤어 합성만 CPU(cv2.warpAffine + numpy 블렌딩)에서 했더니 그 단계 하나가
11.3ms를 먹었다. GPU로 옮기니 2.2ms가 됐다.

## 4. 핵심 설계 결정

### 4.1 CUDA 그래프 — 50ms → 9.2ms

순수 eager 실행은 **입력 해상도를 512에서 224로 낮춰도 50ms에서 안 내려갔다.**
연산이 아니라 커널 실행 오버헤드에 묶여 있었다는 뜻이다(SegFormer는 작은 레이어가
아주 많다). 실행 계획을 통째로 캡처해 재생하니 5배 이상 빨라졌다.

대가: **입력 크기가 고정된다.** 그래서 `INPUT_SIZE=512` 상수이고, 크기가 제각각인
사진을 다루는 오프라인 스크립트는 `use_cuda_graph=False`로 쓴다.

주의: CUDA 그래프는 캡처한 스트림에 묶이므로 **반드시 같은 단일 스레드에서만**
재생해야 한다. 서버가 워커 1개짜리 전용 executor를 쓰는 이유다.

### 4.2 기존 머리 제거 — 인페인팅 대신 시간축 배경 플레이트

기존 시도(TELEA, LaMa)가 실패한 건 알고리즘 문제가 아니라 **정보 부재**였다.
정지 사진 한 장에는 "머리 뒤에 뭐가 있었는지"가 애초에 없으니 모델은 지어낼
수밖에 없고, 그래서 머리 있던 자리가 머리스럽게 채워졌다.

영상은 다르다. 고개를 조금만 돌려도 가려졌던 픽셀이 **실제로 드러난다.**

```
매 프레임:  머리가 아닌 픽셀을 그 위치에 기록 (처음 보면 그대로, 이미 봤으면 EMA)
제거 시점:  기록이 있는 픽셀만 그 값으로 채움. 없으면 원본을 남김(환각하지 않음)
```

두 가지가 중요하다:

- **"배경"이 아니라 "머리가 아닌 것" 전부를 누적한다.** 그래야 머리 뒤가 배경이든
  옷이든 목이든 귀든 한 가지 방법으로 처리된다.
- **근거 없는 픽셀은 안 채운다.** 지워지지 않은 부분은 버그가 아니라 "아직 데이터가
  없다"는 정직한 표시다. 고개를 돌리면 저절로 채워진다.

플레이트에는 알파 < 0.2인 "확실히 머리가 아닌" 픽셀만 넣는다. 경계의 애매한 픽셀까지
넣으면 머리 색이 스며들어 지운 자리에 얼룩이 남는다.

세션(연결)마다 독립적인 플레이트를 갖는다.

### 4.3 마스크 해상도 — 순서가 해상도보다 중요했다

SegFormer 로짓은 입력의 1/4 해상도(512→128)로 나온다. 처음엔 여기서 바로 `argmax`
하고 nearest로 640x480까지 확대했더니 한 칸이 출력 4~5픽셀이 되어 계단이 그대로 보였다.

**argmax를 먼저 하면 그 순간 클래스 번호만 남고 경계의 미세 정보가 사라진다.**
그 뒤엔 아무리 확대해도 복구가 안 된다. 로짓을 bilinear로 먼저 확대한 뒤 argmax하면
경계가 로짓의 연속적 변화를 따라가 출력 해상도만큼 촘촘해진다. **비용 0.1ms.**

입력을 384→512로 올린 건(로짓 96→128) 추가 개선이지만 +3.2ms이고, 순서 수정이
훨씬 값싼 개선이었다.

### 4.4 소프트 알파 경계

해상도를 올려도 마스크를 0/1로 자르면 경계는 딱딱하다.
`sigmoid((머리 로짓 − 나머지 최대) × SOFT_K)`로 0~1 알파를 만들어 블렌딩한다.
`SOFT_K`(기본 1.5)를 낮추면 더 번지고 올리면 선명해진다.

### 4.5 헤어 정합 — 어파인이 아니라 닮음변환

3점 어파인은 전단(shear)까지 허용해서 세그멘테이션이 조금만 흔들려도 헤어가
비스듬히 찌그러진다. 헤어에 전단은 필요 없으므로 **눈 2점 → 균등 스케일 + 회전 +
이동**으로 자유도를 줄였다. 훨씬 안정적이다.

### 4.6 앵커 — 별도 랜드마크 모델 없이

19클래스 파싱에 `l_eye`, `r_eye`, `nose`, `l_brow`, `r_brow`가 들어있으므로
**무게중심이 곧 앵커다.** 이미 GPU에 있는 데이터라 추가 비용이 거의 없다.
안경/감은 눈으로 눈이 안 잡히면 눈썹으로 자동 대체한다.

### 4.7 거리 기반 스케일 정규화 — 실제 버그였다

눈 간격만으로 헤어 크기를 정하면 **고개를 옆으로 돌릴 때 투영된 눈 간격이
cos(yaw)만큼 줄어 헤어도 같이 작아진다.** 머리 크기는 그대로인데.

MediaPipe 변환행렬의 `tz`(카메라로부터의 거리)는 **머리를 돌려도 변하지 않으므로**
스케일 기준으로 적합하다. 다만 tz만으로는 픽셀 크기를 못 정하니(초점거리와 개인별
두상 크기를 모름) 자동 캘리브레이션을 건다:

```
정면(|yaw| < 10°)일 때 :  K ← EMA(관측 눈간격 × tz)
항상                   :  보정 눈간격 = K / tz
```

이 한 줄로 세 가지가 동시에 해결된다 — 거리 변화(tz 반영), yaw 단축(tz는 회전 불변),
**개인별 두상 크기**(K가 사람마다 알아서 맞춰짐).

**역할 분리**: 위치·회전은 세그멘테이션 무게중심으로 매 프레임(공짜), 크기 보정은
랜드마커의 무차원 배율 `d_corrected / d_measured`로 4프레임마다. 배율이 무차원이라
세그멘테이션 눈 간격에 그냥 곱하면 된다.

### 4.8 동기화 — 버퍼가 할 수 있는 것과 없는 것

**버퍼는 지연을 줄이지 못한다. 늘려서 맞추는 도구다.** 처리된 영상이 200ms 늦다면
버퍼를 넣어도 250ms가 되지 150ms가 되지 않는다.

실제로 고칠 수 있는 건 **어긋남**이다. 경로 B(`/warp.html`)에서 `<video>`가 실시간으로
흐르고 캔버스 오버레이만 늦게 얹히면 둘이 서로 다른 시점을 보여줘 헤어가 머리에서
떨어진다. 오버레이를 빠르게 만들어도 이 구조에선 절대 안 붙는다(0에 수렴할 뿐 항상 뒤).

해법은 **같은 프레임으로 묶는 것**이다 — 추론 직전에 그 프레임을 캔버스에 직접 그리고
그 위에 오버레이를 얹는다. 화면 전체가 추론 시간만큼 늦어지는 대신 어긋남이 0이 된다.
경로 A는 서버가 아예 합쳐서 보내므로 이 문제가 구조적으로 없다.

경로 A 페이지의 원본 미리보기도 같은 이유로 지연 버퍼를 걸어 큰 화면에 맞춘다.

### 4.9 계측에서 배운 것 (반복하기 쉬운 실수)

- **로그 주기와 스킵 주기가 배수 관계면 통계가 편향된다.** `_LOG_EVERY=30`,
  `infer_every_n=2`였을 때 30의 배수는 항상 짝수라 **추론 프레임만 골라 찍혀서**
  "skip"이 한 번도 안 나왔다. 지금은 소수(31)를 쓴다.
- **`.item()`은 매번 GPU 동기화를 강제한다.** 프레임당 세 번씩 하니 십수 ms가 샜다.
  통계는 5프레임에 한 번만 재고, 잴 때도 한 텐서로 묶어 전송 1회로 끝낸다.
- **rAF는 디스플레이 주사율(60Hz)에 맞춰 돈다.** 웹캠이 30fps면 같은 프레임을 두 번
  추론한다. `requestVideoFrameCallback`은 새 프레임에만 불리고 캡처 시각 메타데이터도 준다.
- **EMA 스무딩은 지연을 만드는 필터다.** k=0.55면 90% 따라잡는 데 3.85샘플(20fps에서
  193ms). "천천히 따라온다"는 증상은 순수 지연이 아니라 1차 저역통과 필터의 정착
  거동이다. 알파-베타 필터로 대체하면 jitter(ALPHA)와 지연(horizon)을 따로 조절할 수 있다.

## 5. 성능 (RTX 4070 SUPER, 640x480 입력)

| 단계 | 비용 |
|---|---|
| 전처리 | 0.7ms |
| 추론 (CUDA 그래프, 512 입력) | 12~13ms |
| 마스크 + 플레이트 + 제거 | ~1ms |
| 헤어 워핑 + 합성 (GPU) | ~2ms |
| **tryon 합계** | **16.4ms (p95 18.2ms)** |
| 랜드마커 상각분 (4프레임당 1회) | ~2ms |
| **총계** | **~18.5ms** — 30fps 예산 33ms의 절반 |

개선 이력:

| 시점 | tryon | 비고 |
|---|---|---|
| MediaPipe CPU | 98ms (세그멘테이션만) | 코어 1개 포화, 확장 불가 |
| SegFormer GPU eager | ~50ms | 커널 런치 바운드 |
| + CUDA 그래프 | 11.7ms | 5배 |
| + CPU 헤어 합성 | 33.4ms | 회귀 — CPU 왕복이 원인 |
| + GPU 헤어 합성 | 11.8ms | |
| + 512 입력 / 촘촘한 마스크 | **16.4ms** | 품질과 교환 |

```
  server.py           aiohttp + aiortc 시그널링/피어, 프레임 루프, 세션 상태
  gpu_segmenter.py    SegFormer + CUDA 그래프, 마스크, 플레이트, 합성  ← 핵심
  face_pose.py        MediaPipe 랜드마커, 3D 포즈, 거리 기반 스케일 캘리브레이션
  hair_asset.py       헤어 에셋 로딩/절차적 생성, 닮음변환
  make_asset.py       [오프라인] 헤어스타일 사진 → 에셋 추출 CLI
  models/             face_landmarker.task, (구) selfie_multiclass tflite
  assets/             <name>.png (RGBA) + <name>.json (눈 앵커)
client/
  index.html/client.js   경로 A — 서버 합성 표시, 모드 전환, 계측 패널
  warp.html/warp.js      경로 B — 로컬 MediaPipe 워핑 + 추적 품질 측정
docs/
  ARCHITECTURE.md        이 문서
```

### 실행

```bash
cd server
python server.py --port 8080 --preload     # --preload: 첫 연결 전에 모델 적재
python make_asset.py photo.jpg --name bob  # 에셋 추출
```

### 모드 (경로 A 드롭다운)

| 모드 | 내용 |

## 7. 미착수 / 다음

### GAN을 붙일 자리

프레임당 실행은 불가능하다(장당 수 초). 실현 가능한 자리는 둘:

1. **오프라인 에셋 공장** — 참고 사진을 정규 포즈로 정규화하고 여러 각도 버전 생성.
   현재 `make_asset.py`가 이 자리의 GAN 없는 버전이고, GAN은 그 앞단에 끼운다.
   각도별 에셋이 생기면 §7의 포즈 대응(Phase 2)이 풀린다.
2. **고화질 캡처 모드** — 프레임 고정 → HairFastGAN → 결과 1장.
   실시간은 워핑, "사진 찍기"는 GAN. 기술 한계를 제품 기능으로 바꾸는 방법.

선행 조건: **VS Build Tools + CUDA toolkit 설치** (StyleGAN2 커스텀 CUDA 연산 컴파일).

### 남은 과제

- [ ] 포즈 대응 — 2D 워핑이 몇 도부터 깨지는지 측정 후, 각도별 에셋 전환/블렌딩
- [ ] 헤어라인 경계 자연스러움 (피부톤 매칭, 조명 정합)
- [ ] 긴 머리가 어깨/옷 위를 덮는 경우 (플레이트로 처리되지만 검증 안 됨)
- [ ] face parsing 파인튜닝 — 대머리/짧은 머리 등 마스크 애매 케이스
- [ ] 동시 사용자 확장 — 현재 GPU 워커 1개 고정
- [ ] 배포/보안 — 현재 인증 없이 공인 IP에 열려 있음(개발 전용)
